# ADR-085 — NATS JetStream es required en todos los profiles non-dev

**Status:** Accepted
**Date:** 2026-08-19

## Context

Durante la auditoría de ADRs se identificó que `profiles/prod.yaml` usa `transport: memstore`, contradiciendo ADR-012 que establece NATS JetStream como el reference event transport. El `durable` profile usa `transport: natsjs` correctamente, pero `prod` (el más restrictivo) usa el fallback.

## Decision

1. **Todos los profiles non-dev (`durable`, `staging`, `prod`, y cualquier futuro profile de окружения) usan `transport: natsjs`** — NATS JetStream es required.

2. **`dev` profile es el único que usa `transport: memstore`** — como entorno de desarrollo local donde NATS es optional.

3. **El fallback graceful de `durable` hacia memstore se elimina** — si NATS no está disponible en un entorno non-dev, el boot falla con mensaje claro. Esto fuerza la operacionalización correcta en staging/prod.

4. **`profiles/prod.yaml` se corrige** de `transport: memstore` a `transport: natsjs`.

## Rationale

1. **ADR-012 es explícito:** "NATS JetStream is the reference event transport." No dice "recommended" o "preferred" — dice reference, que implica required en entornos de producción.

2. **La degradación graceful en durable era una concession para dev/CI** — tiene sentido en `dev` (donde el developer puede no tener NATS corriendo), pero no en `prod`. Producir sin NATS en prod es un configuration error, no una feature.

3. **El argumento de "cost/complexity" para memstore en prod no está documentado en ningún ADR** — no hay análisis de trade-offs que justifique memstore sobre NATS en prod.

4. **Consistencia con el modelo de eventos:** ADR-030 dice que el Graph Journal combina state + causal history. El causal ordering que provee NATS JetStream es parte de esa semántica. Un transport sin ordering garantizado (memstore) no garantiza causal history.

## Consequences

### Positivas
- Perfiles non-dev son consistentes con ADR-012
- Fallo rápido ante configuración incorrecta en prod (fail-fast es preferible a silencio)
- El equipo de operaciones tiene NATS como requirement explícito

### Negativas
- Environments sin NATS disponible (e.g. some CI runners, bare-metal sin contenedor) requieren NATS para bootear en non-dev
- El durable profile ya no degrade gracefully — esto es un breaking change para cualquier script que asuma que durable boots sin NATS

### Trade-offs
- La complexity operacional de NATS es justificada por la semántica de eventos que el sistema requiere
- Para dev local, memstore es suficiente y preferred (no hay reason deoperacionalizar NATS para un developer individual)

## Alternatives considered

| Alternative | Rejected because |
|-------------|------------------|
| NATS required en prod, pero optional en staging | Staging es el rehearsal de prod — si NATS es required en prod, debe serlo en staging |
| Fallback configurable via env var | Configuración por env var es el antipatrón que los profiles resuelven — el profile debe ser autoritativo |
| Solo eliminar el fallback, mantener prod con memstore | Contradice ADR-012 explícitamente |

## Validation / fitness

- `profiles/prod.yaml` tiene `transport: natsjs`
- `profiles/durable.yaml` tiene `transport: natsjs`
- `profiles/dev.yaml` tiene `transport: memstore` (único caso válido de memstore)
- El código en `cmd/golem/bootstrap/bootstrap.go` no hace fallback a memstore en profiles non-dev

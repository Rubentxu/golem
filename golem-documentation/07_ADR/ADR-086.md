# ADR-086 — Benchmark gate para la elección de Graph Database (ADR-013)

**Status:** Accepted
**Date:** 2026-08-19

## Context

ADR-013 ("Graph database choice requires benchmark gate") está en estado **Proposed**, no Accepted. El ADR dice que la elección de graph database se basará en benchmark con workloads GOLEM, no en preferencia personal o marketing.

El Engineering Graph es el modelo canónico de dominio (ADR-004). Actualmente el grafo se proyecta desde el journal en memoria (`adapters/graph/memstore`) y se pierde al reiniciar. ADR-005 y ADR-049 dicen que el grafo es rebuildable from journal, pero para producción con millones de nodos, rebuild from scratch es impráctico.

## Decision

1. **Ejecutar el benchmark gate de ADR-013 antes de M9.**

2. **Candidate graph databases a evaluar:**
   - **Apache HugeGraph** (original candidate en ADR-013)
   - **NebulaGraph** (comunidad activa, licencia Apache 2.0)
   - **Dgraph** (native GraphQL, LICENSE Apache 2.0, optimized for scale)

   *ArangoDB y Memgraph se evalúan en round 2 si los 3 primeros no superan R4.*

3. **Workloads GOLEM para el benchmark:**
   - **W1: Bulk load** — carga inicial de 100K nodos + 500K aristas (simula migración desde journal)
   - **W2: Neighborhood query** — 1000 queries concurrentes, depth 3, 100 nodos resultado promedio (ADR-056)
   - **W3: Traversal** — 100 traversal queries con múltiples roots, depth 4, con y sin truncation (ADR-056)
   - **W4: Point read** — 10K GetNode por ID (ADR-004)
   - **W5: Mutation rate** — 100 ops/seg de Apply (upsert nodes + edges) durante 60s
   - **W6: Mixed workload** — combinación de W2-W5 con distribución realista (80% reads, 20% writes)

4. **Métricas de evaluación:**
   - Latencia p50, p95, p99 por query type
   - Throughput (ops/seg) en W5 y W6
   - Tiempo de bulk load (W1)
   - Memoria residente durante workload W6
   - Coherencia transaccional: % de reads que ven writes confirmados

5. **Thresholds de accept/reject:**
   - **Required:** Ningún candidato puede fallar W1-W5
   - **R4+** (production-ready): p99 latency W2 < 100ms, throughput W5 > 500 ops/sec
   - **R5** (strategic): además de R4, support de streaming traversal y schema evolution
   - **Reject:** cualquier candidato que falle W6 con más de 1% error rate

6. **Infra de benchmark: Containerfiles + Makefile en `infra/`**:
   - Cada candidate tiene su Containerfile bajo `infra/{hugegraph,nebula,dgraph}/`
   - `infra/Makefile` con targets `bench-{candidate}-up/down` y `bench-{candidate}` con health checks
   - `infra/bench/run.py` — runner con TCK validation + R4 assessment
   - `infra/bench/workloads.py` — W1-W6 workload generators basados en el domain model de ADR-004
   - `infra/bench/clients/` — DB-specific clients (Gremlin para HugeGraph, nGQL para NebulaGraph, GraphQL± para Dgraph)

7. **El resultado del benchmark gate es un ADR nuevo** (ADR-087 o superior) que elige el graph DB con rationale basada en evidencia, o bien declara que el journal como source of truth es suficiente por ahora.

## Rationale

1. **Decisiones costosas requieren evidence.** ADR-013 estableció el principio: la graph DB no se elige con preferencia, se elige con benchmark. No hacerlo es exactamente el anti-patrón que ADR-013 previene.

2. **ADR-004 + ADR-005 están en tensión.** ADR-004 dice que el Engineering Graph es el modelo canónico. ADR-005 dice que el journal es la historia causal. Si el grafo es canónico, debe ser persistente. Si el journal es suficiente, el grafo puede ser rebuildable. Esta tensión se resuelve con evidencia de benchmark: ¿cuánto cuesta rebuild? ¿Cuánto cuesta mantener el grafo sincronizado?

3. **El benchmark gate ya tiene candidatos y metodología.** ADR-013 nombró HugeGraph. Los candidatos adicionales se seleccionan por: license (Apache 2.0 preferred), operability (K8s deployable), y comunidad (active maintenance).

4. **M8 closure no debe esperar al benchmark.** Si el benchmark gate toma más de lo esperado, M8 puede cerrarse con grafo rebuildable (memstore) y ADR-013 queda como spike para M9.

## Consequences

### Positivas
- Decisión de graph DB basada en evidencia, no en preferencia
- Infra reproducible para benchmarks (Containerfiles versionados en el repo)
- Si el benchmark revela que el journal es suficiente, se elimina la complexity de una graph DB

### Negativas
- Requiere setup de múltiples graph databases para benchmark
- El benchmark gate puede tomar 2-3 sprints

### Trade-offs
- Containerfiles estables en el repo vs ephemeral: más reproducible pero más mantenimiento

## Open Questions (a resolver en el benchmark)

| Question | Relevance |
|----------|-----------|
| ¿El grafo debe ser strongly consistent o eventually consistent? | Afecta la choice de graph DB significativamente |
| ¿Cuál es el tamaño máximo de grafo en prod? | Determina si un benchmark con 100K nodos es representativo |
| ¿El grafo necesita streaming subscriptions? | HugeGraph y NebulaGraph tienen approaches diferentes |
| ¿Schema evolution es requerida? | Afecta qué candidatos pueden satisfacer R5 |

## Validation / fitness

- `infra/` contiene Containerfiles funcionales para HugeGraph, NebulaGraph y Dgraph
- `infra/bench/run.py` + `workloads.py` ejecutan W1-W6 contra cada candidate
- TCK validation integrado en el runner (verifica sémantica Golem)
- El benchmark se ejecuta en CI antes de M9
- El ADR resultante del benchmark (ADR-087+) tiene rationale cuantitativa

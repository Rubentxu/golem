# ADR-079: DR Automation

**Status**: Accepted

**Date**: 2026-08-18

## Context

M8 (GA release) requires a disaster recovery capability that produces verifiable,
point-in-time snapshots of the journal and supports cross-region restore
(REQ-DR-001 through REQ-DR-003). This ADR describes the bbolt backup/restore
implementation and the TCK tests that verify correctness.

## Decision

We will implement DR automation with the following characteristics:

### 1. Backup (REQ-DR-001)

```go
// BackupHandle identifies a journal backup (REQ-DR-001).
type BackupHandle struct {
    ID        string `json:"id"`
    Path      string `json:"path"`
    Digest    string `json:"digest"` // sha256 of backup content
    SizeBytes int64  `json:"size_bytes"`
}

// JournalStore.Backup creates a consistent point-in-time snapshot.
Backup(ctx context.Context) (BackupHandle, error)

// ErrBackupInProgress is returned when a backup is already running.
```

The bbolt adapter implements `Backup` by calling `bbolt.Tx.Copy` while holding
a read lock, producing a consistent snapshot without blocking readers.

### 2. Restore (REQ-DR-002)

```go
// JournalStore.Restore restores from a backup handle.
Restore(ctx context.Context, handle BackupHandle) error

// ErrRestoreMismatch is returned when the backup digest does not match.
var ErrRestoreMismatch = errors.New("journal: restore digest mismatch")

// ErrRestoreNotEmpty is returned when Restore is called on a non-empty journal.
var ErrRestoreNotEmpty = errors.New("journal: restore requires empty journal")
```

Restore flow:
1. Verify journal is empty (`Head() == 0`), return `ErrRestoreNotEmpty` if not
2. Copy backup file to journal path
3. Compute sha256 of restored content
4. Compare against `handle.Digest`, return `ErrRestoreMismatch` if mismatch
5. Open the restored bbolt database

### 3. DR TCK Tests (REQ-DR-003)

Three TCK tests verify the DR invariants:

- `TestJournal_BackupCreatesConsistentSnapshot`: backup is readable and consistent
- `TestJournal_RestoreReplaysDigest`: restored journal digest matches backup handle
- `TestJournal_RestoreDrillInCI`: restore works in CI environment (Docker volume)

### 4. sha256 Verification

Every backup/restore cycle verifies integrity using SHA-256. The digest is stored
in the `BackupHandle` at backup time and verified at restore time. This ensures
that silent data corruption is detected before the journal is opened.

## Consequences

- **Positive**: Verifiable disaster recovery with cryptographic integrity checks.
- **Positive**: bbolt `Tx.Copy` provides consistent snapshots without downtime.
- **Positive**: TCK tests provide confidence in DR correctness.
- **Negative**: Restore requires an empty journal (existing data is not merged).
- **Negative**: Large journals may take time to back up and restore.

# ADR-072: Release Agent — Evidence-Based Release Approval Proposal

## Status
Accepted

## Date
2026-08-18

## Context

The agentic layer requires automated evaluation of release readiness based on the full evidence chain (SBOM, VEX, attestations). The Release agent:
1. Subscribes to `release.candidate.v1` and `proposal.applied.v1` events
2. Uses `ReleaseEvidenceLens` to gather the evidence chain
3. Calls LLM to evaluate if the release meets approval criteria
4. Outputs `Proposal{Operations:[UpdateNode{Release.status=approved}]}` through the proposal lifecycle

This ADR defines the Release agent behavior.

## Decision

### Agent Profile

| Field | Value |
|-------|-------|
| ID | `agent.release` |
| Version | `v1` |
| Kind | `Agentic` |
| Event Subscription | `release.candidate.v1`, `proposal.applied.v1` |
| Lens | `ReleaseEvidenceLens` |

### Prompt Design (R-1 Mitigation)

The prompt template is a **compile-time constant**. Dynamic data from the lens is injected as structured JSON.

```
You are the GOLEM Release Agent.
[Static instructions...]
Input Data (from graph lens):
{structured JSON lens result}
```

### Lens Spec

```go
ReleaseEvidenceLens(roots=[release_id], depth=5, maxNodes=500, maxEdges=1000)
```

Traversal: Release → RELEASED_AS → Artifact → SBOM → PackageComponent, with VEX statements (AFFECTED_BY / MITIGATED_BY) attached.

### LLM Evaluation Criteria

The LLM evaluates:
1. **Attestation completeness**: All required attestations present and signed
2. **VEX state**: Vulnerabilities marked "fixed" or "not_affected", none "under_review" or "known_affected"
3. **Severity**: High/critical vulnerabilities must have "fixed" VEX state

### Output

Returns `behavior.HandlerOutput` with:
- `Proposals[]`: `ProposalNote` with approval/rejection rationale
- `Events[]`: `agent.llm.call.completed.v1` with redacted summary

No direct mutation. Policy gate enforces human approval for release.status changes.

### Held-Out Fixture

```
internal/agent/harness/fixtures/cases/v1/release/cve-blocker.json
internal/agent/harness/fixtures/cases/v1-held-out/release/release-with-signature-invalid.json
```

The held-out fixture tests attestation signature validation: unsigned/invalid attestation should block approval.

## Consequences

### Positive
- Automated release readiness evaluation reduces manual review
- Evidence-based reasoning is auditable and deterministic
- Static prompt template mitigates prompt injection

### Negative
- LLM may misjudge edge cases in evidence chain
- Requires tenant-specific policy for approval thresholds

### Risks & Mitigations
- **Prompt injection**: Static template + Redactor (ADR-066)
- **Incomplete evidence**: Policy gate requires human approval
- **VEX manipulation**: VEX attestations must be signed

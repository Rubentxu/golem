# ADR-065 — Proposal Lifecycle and Change Proposals

**Status:** Accepted
**Date:** 2026-08-18

## Context

M7 introduces agents into the authority plane of GOLEM. Agents cannot
directly mutate privileged state (no direct writes). All privileged mutations
must go through a **proposal** that is journaled, policy-evaluated, and
optionally approved before application.

This ADR defines the Proposal lifecycle, the ProposalStore port, and the
command handlers that enforce the policy gate.

## Decision

### 1. Proposal Lifecycle (5 states)

```
draft → proposed → approved → applied
                 ↘ rejected
                 ↘ conflicted
```

- **draft**: initial state (optional, not enforced)
- **proposed**: agent submitted the proposal; policy evaluation required
- **approved**: a human or policy explicitly approved
- **rejected**: approval denied
- **applied**: proposal operations executed on the target
- **conflicted**: concurrent apply detected via optimistic revision

### 2. Proposal Event Types (journal)

| Event | Stream | Trigger |
|---|---|---|
| `proposal.proposed.v1` | `proposal:{id}` | agent submits proposal |
| `proposal.approved.v1` | `proposal:{id}` | human/policy approves |
| `proposal.rejected.v1` | `proposal:{id}` | approval denied |
| `proposal.conflicted.v1` | `proposal:{id}` | revision drift on apply |
| `proposal.applied.v1` | `proposal:{id}` | operations applied |

### 3. ProposalStore Port

```go
type ProposalStore interface {
    Append(ctx context.Context, p Proposal) error
    Get(ctx context.Context, id string) (Proposal, error)
    List(ctx context.Context, tenantID string) ([]Proposal, error)
    Replay(ctx context.Context, tenantID string) ([]Proposal, error)
    UpdateStatus(ctx context.Context, id string, expectedRevision uint64, newStatus string) error
}
```

- `Append` is called after `proposal.proposed.v1` is journaled.
- `UpdateStatus` uses optimistic locking (`expectedRevision`) to detect drift.
- Journal remains source of truth; ProposalStore is the typed projection for application code.

### 4. Policy Gate

- `agent` actors proposing mutations: `PolicyEvaluator.Evaluate` MUST return `ALLOW` before any status transition to `approved` or `applied`.
- Human actors: default allow for approval transitions.
- DENY path emits `proposal.rejected.v1` or `proposal.conflicted.v1` — no direct writes.

### 5. Optimistic Revision

- Each proposal has a monotonically increasing `Revision` field.
- Apply operations read the proposal stream head via `journal.ReadStream`.
- If observed version != expected version, `ErrVersionConflict` is returned and `proposal.conflicted.v1` is emitted.

## Consequences

### Positive

- Agents cannot bypass policy — every mutation is gated.
- Proposals are journaled as immutable events (audit trail).
- Optimistic revision prevents lost updates.
- Conflict detection enables safe concurrent apply.

### Negative

- Adds latency to agent mutation paths (policy evaluation + journal append).
- ProposalStore adds a new interface to implement for each storage adapter.

# ADR-055 — Vulnerability and VEX as first-class graph data

**Status:** Accepted (Supersedes ADR-026)
**Date:** 2026-08-17

## Context

GOLEM debe representar vulnerabilidades y declaraciones VEX como datos del Engineering Graph para que la gate v2 pueda evaluar exposición real (no solo severidad nominal). ADR-026 nombró a VEX como dato de primera clase pero quedó como stub sin taxonomía de status, sin semántica de mitigación y sin integración en la política de gate. La práctica industria distingue cuatro status VEX (not_affected, affected, fixed, in_remediation) con consecuencias distintas sobre la decisión de promoción, y la confianza en una declaración VEX depende de quién la emite.

## Decision

Vulnerabilidades y VEX se proyectan como dos nodos con semántica precisa:

- `Vulnerability` (id = `vuln-<vulnerability_id>`) donde `vulnerability_id` es CVE o GHSA. Lleva atributos `severity ∈ {low, medium, high, critical}` y `status ∈ {open, fixed, disputed}`.
- `VEXStatement` (id = `vex-<statement_id>`) con atributo `status ∈ {not_affected | affected | fixed | in_remediation}` y `justification`.
- Arista `AFFECTED_BY` desde el `PackageComponent` al `Vulnerability` (component → vulnerability).
- Arista `MITIGATED_BY` desde el `Vulnerability` al `VEXStatement`, creada **solo cuando** el status del VEX es `not_affected` o `fixed`. Para `affected` e `in_remediation` la arista no se crea y la gate trata la vulnerabilidad como viva.

La semántica de la gate: una vulnerabilidad se considera mitigada para un component path cuando existe al menos una arista `MITIGATED_BY` desde la vulnerabilidad hasta un `VEXStatement` cuya `product` (artifact_digest o product_purl) coincide con el path. La confianza en el issuer (firma del VEX) queda diferida a la gate handler v3; M4 acepta VEX statements por id y status sin verificar issuer.

El feed de vulnerabilidades es un ingest translator (`VulnerabilityFeed`), no un puerto, porque es una frontera de traducción OSV/GHSA → evento, no un seam crítico de cómputo.

## Rationale

Modelar vulnerabilidades como nodos con `AFFECTED_BY` permite blast radius inverso (vulnerability → affected components → release candidates) sin joins SQL ni agregaciones downstream. Limitar `MITIGATED_BY` a `not_affected|fixed` codifica el contrato VEX (CycloneDX VEX, OpenVEX) sin ambigüedad: `affected` e `in_remediation` siguen siendo exposición viva y deben contar como rojo en la gate. Diferir VEX trust root a gate v3 evita scope creep en M4 (la decisión ya está tomada por user-direction: el outcome de M4 es `vulnerable component → affected release candidates`, no trusted VEX). Tratar el feed como translator (no port) preserva ADR-045: el puerto sería crítico solo si hubiera cómputo propio, pero el cómputo de vulnerabilidad es externo (OSV API, GHSA API) y la canonicalización ocurre en el translator.

## Consequences

### Positivas

- Decisión explícita y verificable vía 4 escenarios spec que cubren CVE conocido, purl desconocido, VEX `not_affected` y VEX `affected`.
- Reduce acoplamiento a taxonomías externas: el nodo `Vulnerability` es canonical y los adapters traducen CVE/GHSA/etc. al nodo.
- Semántica `MITIGATED_BY` solo para `not_affected|fixed` codifica el contrato VEX directamente en el grafo, sin lógica condicional en la gate.
- Blast radius inverso (`Vulnerability → component → SBOM → Artifact → Release`) es un walk tipado y acotado, no un join (ADR-056).
- Diferir trust root a v3 previene scope creep y mantiene M4 entregable.

### Trade-offs

- Aceptar VEX sin firma en M4 es un trade-off explícito: falsos negativos son posibles si un atacante publica un VEX `not_affected` propio. Mitigación: gate v3 issuer trust + audit log de VEX statements.
- Atributo `severity` libre (cualquier string) puede diverger entre feeds; gate v2 filtra por `{high, critical}` como baseline; feeds deben canonicalizar.
- `vulnerability_id` se trata como opaco (prefijo `vuln-` + id), lo que impide queries por rango de severidad sobre el ID; la severidad debe consultarse como atributo.
- El feed es translator, no port: si OSV o GHSA cambian de modelo, el translator debe actualizarse, sin TCK que avise de regresión. Mitigación: unit tests por feed con fixtures `osv-sample.json`, `ghsa-sample.json` en `testdata/supplychain/`.
- VEX `in_remediation` cuenta como exposición viva — puede generar rojos masivos durante remediaciones legítimas; la operatoria debe correlacionar `in_remediation` con sprints de fix.

## Alternatives considered

- **VEX como atributo de `Vulnerability` (no nodo separado)**: rejected — pierde la justificación como dato auditable y complica múltiples VEX por vulnerabilidad (producto distinto, justificación distinta).
- **`MITIGATED_BY` para todos los status VEX**: rejected — viola el contrato CycloneDX/OpenVEX donde `affected` e `in_remediation` declaran exposición viva.
- **VEX trust root en M4**: rejected por scope (user-direction explícita: M4 cierra `vulnerable component → release candidates`, no VEX signed-trust). Queda en gate handler v3.
- **`VulnerabilityFeed` como puerto con TCK**: rejected — no hay cómputo crítico detrás, solo traducción; un TCK aquí duplicaría fixtures del translator.
- **Vulnerabilidades embebidas en `SBOM` (modelo CycloneDX nativo)**: rejected — CycloneDX VEX se separa del SBOM por diseño y dos feeds distintos pueden reportar la misma vuln contra el mismo component con temporalidad distinta.

## Validation / fitness

- Escenarios spec cubiertos 1:1: `ScenarioCVEReportedAgainstKnownComponent`, `ScenarioUnknownPurlYieldsZeroAffectedEdges`, `ScenarioNotAffectedVEXSuppressesGateFinding`, `ScenarioAffectedVEXDoesNotSuppress`.
- Unit test `TestVEXMitigationSemantics` que aplica 4 VEX statements con cada status y verifica la creación/no creación de `MITIGATED_BY`.
- Unit test `TestVulnerabilityReportedAgainstUnknownPurl` que verifica `affected=0` y no edge.
- `TestGateV2ReasonCodes` cubre `vuln_unmitigated:<id>` para severity `high`/`critical` sin `MITIGATED_BY`.
- Idempotencia demostrada por `TestVulnerabilityFeedIdempotent` con el mismo `(provider, vulnerability_id, component_purl)` reentregado.
- `internal/archtest` rechaza `github.com/google/osv-scanner`, `github.com/aquasecurity/trivy` etc. en `internal/`; los translators viven en `adapters/registry/translators/`.

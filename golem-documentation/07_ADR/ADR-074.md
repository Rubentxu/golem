# ADR-074: Multi-cell Data Partitioning

**Status**: Accepted

**Date**: 2026-08-18

## Context

M8 introduces multi-cell architecture as the data partitioning strategy for GOLEM SaaS.
Each cell is an isolated unit of data (journal + graph) serving a subset of tenants.
Cell routing determines which cell a tenant's requests are routed to.

## Decision

We will implement cell-based data partitioning with the following characteristics:

1. **Cell as Isolation Boundary**: Each cell has its own journal and graph store.
   All events for a tenant are partitioned to a single cell.

2. **CellRouter Port**: A `CellRouter` port provides `Route(ctx, tenantID) → CellID`
   deterministically. Same tenantID always maps to the same cell while no migration
   is in progress.

3. **Cell Health Monitoring**: Each cell reports health via `CellRouter.Health(cellID)`
   with lag, journal head position, and status.

4. **Drain and Promote**: Cells can be drained (stop accepting new appends) and
   promoted (become writable after being drained).

5. **LRU Cache with TTL**: The router caches cell assignments with a 5-minute TTL
   to balance performance and consistency.

6. **Cell Lifecycle Events**: `cell.promoted.v1`, `cell.demoted.v1`, and
   `cell.routing.conflict_detected.v1` are emitted on state changes.

## Consequences

- **Positive**: Natural tenant isolation, enables cell-level operations (drain, migrate).
- **Positive**: Deterministic routing enables sticky sessions and cache-friendly behavior.
- **Negative**: Cross-cell queries require explicit routing or federation.
- **Negative**: Cell failure requires re-routing of affected tenants.
